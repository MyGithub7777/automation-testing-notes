Session 1 — BDD, Cucumber & Gherkin Fundamentals

Session 1 — BDD, Cucumber & Gherkin Fundamentals

Beginner FriendlyTheory + ExamplesPlaywright BDD Focus

Learning objective: Understand BDD, Cucumber, and Gherkin, and learn how to write professional .feature files before integrating them with Playwright and TypeScript.

1. What is BDD?

BDD stands for Behavior-Driven Development.

BDD is a software development approach that focuses on how an application should behave from the user's perspective.

It encourages collaboration between:

  • Business Analysts (BA) / Product Owners (PO)

  • Developers

  • Testers / QA Engineers

In BDD, we describe application behavior using simple, understandable language rather than technical automation code.

Example: Login functionality

Imagine a requirement:

A registered user should be able to log in using valid credentials and see the dashboard.

Without BDD, a tester might immediately write automation code to fill username and password fields.

With BDD, the expected behavior is described first:

gherkin
Feature: Login functionality

  Scenario: Successful login
    Given User is on the login page
    When User enters valid credentials
    Then User should see the dashboard

This scenario can be understood by a business analyst, developer, or tester without knowing TypeScript.

BDD workflow

Business Requirement

User should log in successfully

BDD Discussion

BA + Developer + QA agree on behavior

Gherkin Scenario

Given → When → Then

Automation Implementation

Playwright + TypeScript

Test Execution & Results

Pass / Fail

Advantages

Disadvantages

When should we use BDD?

BDD is useful when requirements change frequently, the team follows Agile development, and business stakeholders want to understand test coverage.

For a very small project without business collaboration, BDD may introduce unnecessary overhead.

2. What is Cucumber?

Cucumber is an open-source BDD tool that connects business-readable scenarios with automation code.

It uses Gherkin syntax to describe application behavior.

Cucumber-style scenarios are written in .feature files.

3. What is Gherkin?

Gherkin is a simple, structured language used to describe application behavior.

It uses keywords such as Feature, Scenario, Given, When, and Then.

Gherkin scenarios are saved in files with the .feature extension.

Gherkin keywords

Keyword

Purpose

Feature

Describes the functionality being tested

Scenario

Represents one test case

Given

Defines the initial condition

When

Describes an action

Then

Describes the expected result

And

Adds another related step

But

Describes an exception or contrast

Background

Common steps for scenarios

Scenario Outline

Runs the same scenario with different data

Examples

Supplies data for Scenario Outline

Rule

Groups scenarios by business rule

Example feature file

gherkin

Feature: Login functionality
  Users should be able to log in
  using valid credentials.

  Scenario: Successful login
    Given User is on the login page
    When User enters valid username and password
    Then User should see the dashboard

  Scenario: Login with invalid credentials
    Given User is on the login page
    When User enters invalid username and password
    Then User should see an error message

One feature can contain multiple scenarios. Each scenario should test one specific behavior.

4. Given, When, Then, And, But

These are the most commonly used Gherkin keywords.

Given

Initial condition

When

User action

Then

Expected result

Given → When → Then describes the complete behavior of a scenario.

Given — Preconditions

Defines the initial state before performing an action.

gherkin
Given User is on the login page

Other examples:

gherkin
Given User is logged into the application
Given User has products in the cart

When — Action

Describes what the user does.

gherkin
When User enters valid credentials

Other examples:

gherkin
When User clicks the login button
When User adds a product to the cart

Then — Expected result

Describes what should happen after the action.

gherkin
Then User should see the dashboard

Other examples:

gherkin
Then User should see an error message
Then Cart should contain one product

And / But — Additional steps

And adds another step of the same kind. But describes a contrasting condition or outcome.

gherkin
Scenario: Login with empty password
  Given User is on the login page
  And User has a registered account
  When User enters a valid username
  But leaves the password empty
  Then User should see a validation message
  And User should remain on the login page

Best practice: Keep scenarios focused on business behavior, not technical details such as CSS selectors, XPath, or browser commands.

5. What is Background?

Background is used when multiple scenarios in the same feature require common setup steps.

Background steps execute before each scenario in their scope.

Without Background

gherkin
Feature: Login

  Scenario: Valid login
    Given User is on the login page
    When User enters valid credentials
    Then User should see the dashboard

  Scenario: Invalid login
    Given User is on the login page
    When User enters invalid credentials
    Then User should see an error message

Notice that the Given step is repeated.

With Background

gherkin
Feature: Login

  Background:
    Given User is on the login page

  Scenario: Valid login
    When User enters valid credentials
    Then User should see the dashboard

  Scenario: Invalid login
    When User enters invalid credentials
    Then User should see an error message

Execution flow

Background

Given User is on the login page

Scenario 1

Background → Valid login → Verify dashboard

Scenario 2

Background → Invalid login → Verify error

Background does not execute just once for the entire feature. It runs for every scenario.

Use Background only for short, common preconditions. Do not use it for unrelated setup.

6. Scenario Outline and Examples

A Scenario Outline allows the same scenario to run with multiple sets of test data.

It is one of the most important Gherkin concepts for data-driven testing.

Example

gherkin
Feature: Login functionality

  Scenario Outline: Login with multiple users
    Given User is on the login page
    When User enters "<username>" and "<password>"
    Then User should see "<message>"

    Examples:
      | username   | password | message             |
      | admin      | admin123 | Welcome Admin       |
      | user1      | wrong123 | Invalid credentials |
      | lockedUser | lock123  | Account locked      |

How Scenario Outline works

Each row in the Examples table creates a separate scenario execution.

Execution

Password

Expected result

Welcome Admin

2

wrong123

3

1 Scenario Outline + 3 Data Rows = 3 Tests

Each test uses its own values from the Examples table.

Use Scenario Outline when the steps remain the same but the input or expected result changes.

7. Data Tables and Doc Strings

These are additional ways to pass information to Gherkin steps.

Data Tables

A Data Table supplies structured information to a step.

Example: Checkout form.

gherkin
Scenario: Enter checkout details
  Given User is on the checkout page
  When User enters the following details
    | field   | value     |
    | name    | John Doe  |
    | city    | New York  |
    | country | USA       |
  Then User should proceed to payment

The table is passed to the matching step definition, where TypeScript code can read the rows.

Scenario Outline vs Data Table

Scenario Outline

Data Table

Multiple test executions

Usually one scenario execution

Data comes from Examples

Data is passed to a step

Best for testing many input combinations

Best for forms and structured input

Each Examples row becomes a test

Rows do not automatically become separate tests

Doc Strings

Doc Strings pass multiline text to a step.

gherkin
Scenario: Submit a support message
  Given User is on the support page
  When User submits the following message
    """
    Hello Support,
    I cannot access my account.
    Please help me reset my password.
    """
  Then User should see a confirmation message

Doc Strings are useful for long messages, JSON payloads, and other multiline content.

8. What are Tags in Gherkin?

Tags are labels used to organize and filter scenarios.

Tags start with the @ symbol.

Example

gherkin
@regression
Feature: Login functionality

  @smoke
  Scenario: Successful login
    Given User is on the login page
    When User enters valid credentials
    Then User should see the dashboard

  @negative
  Scenario: Invalid login
    Given User is on the login page
    When User enters invalid credentials
    Then User should see an error message

Common tags

Tag

Purpose

@smoke

Critical functionality

@regression

Regression testing

@sanity

Quick validation

@negative

Invalid or error scenarios

@login

Login-related tests

@wip

Work in progress

A feature-level tag applies to all scenarios in that feature. Scenario-level tags apply to their individual scenarios.

In Playwright BDD, tags can be used for test filtering through the Playwright integration. We'll cover the exact execution configuration in Session 2.

9. Rule keyword

Rule groups scenarios that belong to the same business rule.

For example, a login feature can contain rules for successful and unsuccessful authentication.

gherkin
Feature: Login functionality

  Rule: Valid users can log in

    Scenario: Login with valid credentials
      Given User is on the login page
      When User enters valid credentials
      Then User should see the dashboard

  Rule: Invalid users cannot log in

    Scenario: Login with invalid credentials
      Given User is on the login page
      When User enters invalid credentials
      Then User should see an error message

Use Rule when a feature contains several distinct business rules. For small feature files, it is optional.

11. Complete practical example

Below is a feature file that combines the main concepts from this session.

gherkin

@regression
Feature: Login functionality
  As a registered user
  I want to log in to the application
  So that I can access my account

  Background:
    Given User is on the login page

  Rule: Valid users can access their accounts

    @smoke
    Scenario: Successful login
      When User enters valid credentials
      Then User should see the dashboard

  Rule: Invalid users cannot access their accounts

    @negative
    Scenario Outline: Login with invalid credentials
      When User enters "<username>" and "<password>"
      Then User should see "<message>"

      Examples:
        | username | password | message             |
        | admin    | wrong123 | Invalid credentials |
        | unknown  | pass123  | Invalid credentials |
        | admin    |          | Password is required |

Understand the execution

Login functionality

Scenario

This feature contains 4 test executions: one successful login scenario and three examples of invalid login.
