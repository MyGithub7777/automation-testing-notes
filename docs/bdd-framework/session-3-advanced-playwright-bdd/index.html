2. What are hooks?

Hooks are special functions that execute before or after a scenario or test.

Your S5 notes explain that hooks help with:

  • Setting up and cleaning up test data.

  • Avoiding repeated setup code.

  • Maintaining test independence.

  • Capturing screenshots and logs.

  • Preparing or resetting application state.

Example: BeforeScenario and AfterScenario

Create steps/hooks.ts:

typescript
import { createBdd } from 'playwright-bdd';

const { BeforeScenario, AfterScenario } = createBdd();

BeforeScenario(async ({ page }) => {
  await page.goto('/');
});

AfterScenario(async ({ page }) => {
  await page.close();
});

Important: This illustrates the hook lifecycle, but manually closing the Playwright-managed page is generally unnecessary. Playwright fixtures handle page and context cleanup automatically. In a real project, use the after hook for application-specific cleanup instead.

Better hook implementation

In our framework, use hooks for logging, application preparation, or cleanup. Let Playwright manage browser and page creation.

typescript
// steps/hooks.ts
import { createBdd } from 'playwright-bdd';

const { BeforeScenario, AfterScenario } = createBdd();

BeforeScenario(async () => {
  console.log('Starting BDD scenario');
});

AfterScenario(async () => {
  console.log('BDD scenario finished');
});

For login-specific setup, you can use a conditional hook:

typescript
BeforeScenario(
  { tags: '@login' },
  async ({ page }) => {
    await page.goto('/login');
  }
);

This hook runs only for scenarios carrying the @login tag. Avoid navigating to the login page again in a matching Given step if the hook already performs that action.

3. What are Playwright fixtures?

Fixtures are reusable objects that Playwright creates and supplies to tests.

Playwright already provides built-in fixtures such as page, context, browser, and request.

Fixture

Purpose

page

Interact with a browser tab

context

Manage isolated browser sessions

browser

Access the browser instance

request

Perform API requests

Custom fixture

Supply page objects, test data, or services

Why fixtures instead of Cucumber World?

Your S5 material uses standalone Cucumber's scenario context. For our Playwright-style BDD framework, custom fixtures are a better fit.

They allow us to share objects across steps in one scenario without relying on global variables.

Fixture lifecycle

mermaid
flowchart TD
    A["Scenario starts"] --> B["Playwright prepares fixtures"]
    B --> C["Create page objects and state"]
    C --> D["Given / When / Then steps"]
    D --> E["Scenario finishes"]
    E --> F["Fixture teardown"]
    F --> G["Next scenario gets isolated state"]

Example: Create a custom fixture

Create fixtures/test-fixtures.ts:

typescript
import { test as base, createBdd } from 'playwright-bdd';
import { LoginPage } from '../pages/LoginPage';

type Fixtures = {
  loginPage: LoginPage;
  scenarioState: {
    username?: string;
  };
};

export const test = base.extend<Fixtures>({
  loginPage: async ({ page }, use) => {
    await use(new LoginPage(page));
  },

  scenarioState: async ({}, use) => {
    await use({});
  },
});

export const {
  Given,
  When,
  Then,
  BeforeScenario,
  AfterScenario,
} = createBdd(test);

The LoginPage class will be created in the next section.

Important: Import the base test from playwright-bdd, not @playwright/test, when defining fixtures used by BDD steps. Export the extended test so the generated BDD tests can use it.

Shared state example

typescript
// steps/state.steps.ts
import { Given, Then } from '../fixtures/test-fixtures';
import { expect } from '@playwright/test';

Given(
  'I store username {string}',
  async ({ scenarioState }, username: string) => {
    scenarioState.username = username;
  }
);

Then(
  'the stored username should be {string}',
  async ({ scenarioState }, expected: string) => {
    expect(scenarioState.username).toBe(expected);
  }
);

Feature:

gherkin
Scenario: Share data between steps
  Given I store username "admin"
  Then the stored username should be "admin"

Both steps receive the same scenario-scoped state object. A different scenario receives a new object.

4. Page Object Model (POM)

Page Object Model is a design pattern where we keep page-related locators and actions inside reusable classes.

Without POM, browser actions are written directly in step definitions. With POM, step definitions call meaningful page methods.

Without POM

typescript
When('User enters valid credentials', async ({ page }) => {
  await page.getByLabel('Username').fill('admin');
  await page.getByLabel('Password').fill('admin123');
  await page.getByRole('button', { name: 'Login' }).click();
});

With POM

typescript
When(
  'User enters valid credentials',
  async ({ loginPage }) => {
    await loginPage.login('admin', 'admin123');
  }
);

The second version is easier to reuse and maintain.

Create pages/LoginPage.ts

typescript

import { Page, Locator, expect } from '@playwright/test';

export class LoginPage {
  readonly page: Page;
  readonly usernameInput: Locator;
  readonly passwordInput: Locator;
  readonly loginButton: Locator;
  readonly dashboardHeading: Locator;

  constructor(page: Page) {
    this.page = page;

    this.usernameInput = page.getByLabel('Username');
    this.passwordInput = page.getByLabel('Password');
    this.loginButton = page.getByRole('button', {
      name: 'Login',
    });
    this.dashboardHeading = page.getByRole('heading', {
      name: 'Dashboard',
    });
  }

  async navigate() {
    await this.page.goto('/login');
  }

  async login(username: string, password: string) {
    await this.usernameInput.fill(username);
    await this.passwordInput.fill(password);
    await this.loginButton.click();
  }

  async verifyDashboard() {
    await expect(this.dashboardHeading).toBeVisible();
  }
}

These locators assume your application has accessible labels and a Dashboard heading. Adapt them to your test application.

Create steps/login.steps.ts

typescript

import {
  Given,
  When,
  Then,
} from '../fixtures/test-fixtures';

Given('User is on the login page', async ({ loginPage }) => {
  await loginPage.navigate();
});

When(
  'User logs in with {string} and {string}',
  async ({ loginPage }, username: string, password: string) => {
    await loginPage.login(username, password);
  }
);

Then('User should see the dashboard', async ({ loginPage }) => {
  await loginPage.verifyDashboard();
});

5. Data-driven testing

Your S6 PDF introduces four approaches:

  1. Direct parameterization.

  2. Scenario Outline with Examples.

  3. Data Tables.

  4. External test data (JSON, CSV, database).

All four concepts are relevant to Playwright BDD.

Approach 1 — Direct parameterization

gherkin
Scenario: Login with credentials
  Given User is on the login page
  When User logs in with "admin" and "admin123"
  Then User should see the dashboard

This uses the parameterized login step we already created.

Approach 2 — Scenario Outline + Examples

gherkin
Scenario Outline: Login with different credentials
  Given User is on the login page
  When User logs in with "<username>" and "<password>"
  Then User should see "<message>"

  Examples:
    | username | password | message             |
    | admin    | wrong123 | Invalid credentials |
    | unknown  | pass123  | Invalid credentials |
    | admin    |          | Password is required |

Each Examples row creates a separate test execution.

3 Tests

Generated from one Scenario Outline with three data rows

For this feature, you would add a Then step that checks the actual validation message displayed by your application.

Approach 3 — Data Tables

Data Tables are useful when a step needs multiple related values.

gherkin
Scenario: Fill checkout form
  Given User is on the checkout page
  When User enters checkout details
    | field   | value     |
    | name    | John Doe  |
    | city    | Pune      |
    | country | India     |
  Then Checkout details should be saved

Example TypeScript step:

typescript
import { When } from '../fixtures/test-fixtures';
import type { DataTable } from '@cucumber/cucumber';

When(
  'User enters checkout details',
  async ({ page }, table: DataTable) => {
    const details = table.rowsHash();

    await page.getByLabel('Name').fill(details.name);
    await page.getByLabel('City').fill(details.city);
    await page.getByLabel('Country').fill(details.country);
  }
);

Here, the DataTable import is a type from the Cucumber ecosystem, not a switch to the standalone Cucumber runner. In a playwright-bdd project, prefer the type exports supported by your installed version where available.

Approach 4 — External JSON test data

Create test-data/users.json:

json

{
  "validUser": {
    "username": "admin",
    "password": "admin123"
  },
  "invalidUser": {
    "username": "unknown",
    "password": "wrong123"
  }
}

Use it in a step definition:

typescript
import users from '../test-data/users.json';
import { When } from '../fixtures/test-fixtures';

When(
  'User logs in with the valid test account',
  async ({ loginPage }) => {
    await loginPage.login(
      users.validUser.username,
      users.validUser.password
    );
  }
);

Best practice: Store non-sensitive test data in JSON. Do not commit real passwords, API keys, or production credentials to your repository. Use environment variables or a secrets manager for sensitive values.

6. Tags and test filtering

Tags help us organize scenarios into different test suites.

Example

gherkin
@regression
Feature: Login functionality

  @smoke
  Scenario: Successful login
    Given User is on the login page
    When User logs in with "admin" and "admin123"
    Then User should see the dashboard

  @negative
  Scenario: Invalid login
    Given User is on the login page
    When User logs in with "unknown" and "wrong"
    Then User should see "Invalid credentials"

Tag execution commands

Requirement

Command

Generate all scenarios

npx bddgen

Generate only smoke scenarios

npx bddgen --tags "@smoke"

Generate regression scenarios

npx bddgen --tags "@regression"

Exclude work-in-progress scenarios

npx bddgen --tags "not @wip"

Combine tag conditions

npx bddgen --tags "@smoke and not @wip"

After generation, run:

bash
npx playwright test

The bddgen --tags command filters which BDD scenarios are generated. Regenerate without the filter when you want the full suite again.

For a larger framework, you can also define separate Playwright projects or use Playwright's test filtering options.

7. Reporting, screenshots, videos, and traces

Your S5 PDF covers failure screenshots and reporting. In Playwright BDD, we can use Playwright's built-in reporting and debugging capabilities.

Configure reporting

Update the relevant settings in playwright.config.ts:

typescript

import { defineConfig, devices } from '@playwright/test';
import { defineBddConfig } from 'playwright-bdd';

const testDir = defineBddConfig({
  features: 'features/**/*.feature',
  steps: ['steps/**/*.ts'],
});

export default defineConfig({
  testDir,

  timeout: 30000,

  retries: 1,

  workers: 2,

  reporter: [
    ['list'],
    ['html', { open: 'never' }],
    ['junit', { outputFile: 'reports/results.xml' }],
  ],

  use: {
    baseURL: 'https://your-test-app.example',
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
    trace: 'on-first-retry',
  },

  projects: [
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'] },
    },
  ],
});

The URL above is a placeholder. Replace it with your real test application's URL.

What can you inspect in a trace?

A Playwright trace can include:

  • Actions and their timings.

  • DOM snapshots.

  • Network requests.

  • Console messages.

  • Screenshots and failure context.

You can use these details to understand why a scenario failed.

8. Parallel execution and retries

Parallel execution means running multiple tests simultaneously using Playwright workers.

Example

typescript
export default defineConfig({
  workers: 3,
  retries: 2,
});

This configures up to three workers and allows failed tests to be retried twice.

Worker 2

Combined Test Report

Important parallel execution rules

  • Do not share a single page variable across scenarios.

  • Use test-scoped fixtures for mutable scenario data.

  • Avoid tests depending on execution order.

  • Use unique test accounts or isolated data when scenarios modify shared records.

  • Keep browser sessions independent.

Retry example

Suppose a test fails on the first attempt but passes on the first retry.

With retries: 2, Playwright can retry it up to two times. A test that passes only after retry is reported as flaky rather than a clean first-attempt pass.

Retries help detect instability, but they should not replace fixing unreliable tests.
