2. Understand Playwright BDD architecture

There are three common ways to organize browser tests with Playwright. The main choices are how we describe tests and which test runner executes them.

Approach 1 — Playwright Test with TypeScript

Write tests directly in TypeScript using @playwright/test. Playwright Test runs them and provides fixtures, assertions, reporting, and debugging tools. This is a straightforward choice when the team does not need Gherkin feature files.

Approach 2 — Cucumber.js with the Playwright library

Write Gherkin scenarios and implement step definitions using @cucumber/cucumber. Cucumber.js runs the scenarios, while the Playwright library performs browser actions. Browser setup, cleanup, and integrations are managed through the Cucumber-based framework. This fits a team that wants to keep Cucumber.js as its runner.

Approach 3 — Playwright BDD with TypeScript

Write Gherkin feature files and TypeScript step definitions using the third-party playwright-bdd integration. Its bddgen command generates Playwright tests from those scenarios. Playwright Test then executes the generated tests.

Why are we selecting Playwright BDD?

This course aims to combine business-readable scenarios with Playwright Test execution:

  • Readable behavior: Gherkin describes scenarios that developers, testers, and business stakeholders can review together.

  • Playwright fixtures: Browser contexts and pages can use Playwright's managed setup, isolation, and cleanup.

  • One execution toolchain: Use Playwright Test's configured reporters, traces, retries, parallel workers, and debugging tools.

  • Reusable implementation: TypeScript steps can use Page Object classes and custom fixtures as the framework grows.

Trade-off: Playwright BDD adds an integration dependency, step-definition maintenance, and a test-generation step. If a team does not need Gherkin collaboration, direct Playwright Test may be simpler. For this course, Gherkin is an explicit learning goal, so Playwright BDD fits our chosen approach.

Runner distinction: We use playwright-bdd to connect Gherkin to Playwright Test. We do not run these scenarios with cucumber-js.

Execution flow

1. Feature File

login.feature — Given, When, Then

2. Step Definitions

login.steps.ts — TypeScript automation

3. BDD Generation

bddgen — generates Playwright test files

4. Playwright Test Runner

Runs scenarios using browser fixtures

5. Test Results

Pass / Fail, reports and traces

The key idea is that Gherkin remains the same, but Playwright handles the test execution.

3. Project setup in VS Code

We'll use the public Playwright documentation website for the first working example. This avoids depending on an application with unknown credentials or selectors.

Step 1 — Create a project

Open a terminal in VS Code and run:

bash
mkdir playwright-bdd-framework
cd playwright-bdd-framework

Step 2 — Initialize Playwright and add BDD dependencies

bash
npm init playwright@latest

Run the initializer from the project folder. Choose TypeScript, keep the default tests folder, and choose to install Playwright browsers. A GitHub Actions workflow is optional for this local lesson.

The initializer installs Playwright Test and creates playwright.config.ts, a sample test, and package files. Keep the generated configuration and its browser projects. If you skip browser installation, run npx playwright install later so all configured browsers are available.

Next, add the BDD integration, the TypeScript compiler, and Node.js types:

bash
npm install -D playwright-bdd typescript @types/node

Package

Purpose

@playwright/test

Test runner, browser fixtures, assertions

playwright-bdd

Gherkin integration and test generation

typescript

TypeScript support

@types/node

Node.js TypeScript types

We do not need to install @cucumber/cucumber or ts-node for this setup.

Step 3 — Create the project structure

text
playwright-bdd-framework/
├── tests/                  # Created by the Playwright initializer
│   └── example.spec.ts
├── features/               # Add your Gherkin files here
│   └── navigation.feature
├── steps/                  # Add your step definitions here
│   └── navigation.steps.ts
├── playwright.config.ts    # Keep the generated file; extend it for BDD

├── package-lock.json

The .features-gen folder is generated automatically. We should not manually edit its test files.

5. Configure Playwright BDD

Extend the playwright.config.ts created by the initializer. Do not replace the generated configuration with a separate minimal file.

Keep the existing imports, defineConfig() call, browser projects, reporters, retry settings, and other generated options. Add the following import alongside the existing imports, then declare testDir before the existing export default defineConfig(...):

typescript
// Add this import alongside the existing imports.
import { defineBddConfig } from 'playwright-bdd';

// Add this before the existing export default defineConfig(...).
const testDir = defineBddConfig({
  features: 'features/**/*.feature',
  steps: 'steps/**/*.ts',
});

  1. In the existing configuration object, replace testDir: './tests', with testDir,. Use the initializer's equivalent path if its test folder name differs.

  2. Inside the existing use object, add or uncomment baseURL: 'https://playwright.dev',. Keep the other use settings. The lesson uses page.goto('/'), which needs this base address.

  3. Leave the remaining generated options unchanged. Keep all configured browser projects and install their browsers. Each BDD scenario runs once per configured browser project. Set screenshots or other optional settings only when you want to customize them.

Why are small changes still needed? The generated config searches the sample-test folder. BDD must point Playwright at the tests produced by bddgen. We retain the generated file and defaults, adding only the BDD wiring and the base URL used in this lesson.

Keep tests/example.spec.ts if you want the starter example. Once testDir points to the generated BDD directory, that sample is no longer included in this BDD run. Run npx bddgen before executing the BDD tests, as shown in Section 9.

7. Create TypeScript step definitions

Create:

steps/navigation.steps.ts

typescript

import { createBdd } from 'playwright-bdd';
import { expect } from '@playwright/test';

const { Given, When, Then } = createBdd();

Given(
  'I am on the Playwright homepage',
  async ({ page }) => {
    await page.goto('/');
  }
);

When(
  'I click the {string} link',
  async ({ page }, linkName: string) => {
    await page
      .getByRole('link', { name: linkName, exact: true })
      .click();
  }
);

Then(
  'the page URL should contain {string}',
  async ({ page }, expectedText: string) => {
    await expect(page).toHaveURL(
      new RegExp(expectedText)
    );
  }
);

The createBdd() function provides step registration functions. Playwright-style steps receive fixtures as the first argument and Gherkin parameters afterward.

GitHub

How step matching works

Matches the step pattern

Extracts parameter

Understanding the code

createBdd()

Creates the Given, When, and Then functions for registering BDD steps.

async ({ page })

Gets the Playwright page fixture. Playwright manages the page and its browser context for the test.

await page.goto('/')

Navigates to the configured baseURL.

page.getByRole('link', { name: linkName })

Finds a link using its accessible role and name.

expect(page).toHaveURL()

Checks the URL using Playwright's auto-retrying assertion.

8. Parameterization in step definitions

Parameterization allows one step definition to work with multiple values.

Example: String parameter

Feature file:

gherkin
When I click the "Get started" link

Step definition:

typescript
When(
  'I click the {string} link',
  async ({ page }, linkName: string) => {
    await page
      .getByRole('link', { name: linkName })
      .click();
  }
);

The {string} placeholder captures the quoted value.

Example: Integer parameter

gherkin
Then the cart should contain 3 products
typescript
Then(
  'the cart should contain {int} products',
  async ({ page }, count: number) => {
    await expect(
      page.locator('[data-testid="cart-item"]')
    ).toHaveCount(count);
  }
);

The cart selector is illustrative; it requires an application with matching elements.

Example: Multiple parameters

gherkin
When User enters "admin" and "admin123"
typescript
When(
  'User enters {string} and {string}',
  async ({ page }, username: string, password: string) => {
    await page.getByLabel('Username').fill(username);
    await page.getByLabel('Password').fill(password);
  }
);

Here, two values are extracted from the Gherkin step and passed to the TypeScript function.

9. Generate and execute BDD tests

Unlike standalone Cucumber, playwright-bdd has a generation phase followed by Playwright execution.

Step 1 — Generate tests

Run:

bash
npx bddgen

This reads your feature files and step definitions and generates Playwright-compatible test files.

Step 2 — Execute tests

bash
npx playwright test

To run both steps together:

bash
npx bddgen && npx playwright test

This two-stage approach is also used by the official playwright-bdd example project.

GitHub

Step 3 — Add npm scripts

Update the scripts section of package.json:

json

{
  "scripts": {
    "bddgen": "bddgen",
    "test": "bddgen && playwright test",
    "test:headed": "bddgen && playwright test --headed",
    "test:ui": "bddgen && playwright test --ui",
    "test:debug": "bddgen && playwright test --debug",
    "report": "playwright show-report"
  }
}

This is the scripts section only; retain the dependencies and other fields already in your package.json.

Now run:

bash
npm test

Expected execution

If the website and its navigation remain unchanged, the expected result is similar to:

text
Running 1 test using 1 worker

  ✓ Open the installation documentation

  1 passed

This is illustrative output, not a claim that the test was executed here.

VS Code — Navigate from feature steps to step definitions

To use Ctrl+Click or F12 on a Gherkin step, the editor extension needs to find your feature files and step-definition files. The extension is optional for running tests, but provides this navigation in the editor.

If you installed Cucumber by Cucumber, create .vscode/settings.json in your automation project's root folder:

.vscode/settings.json
{
  "cucumber.features": ["features/**/*.feature"],
  "cucumber.glue": ["steps/**/*.ts"]
}

These paths assume your folders are named features and steps. Adjust them to match your project. The extension's default search paths may miss a separate steps folder.

  1. Open the automation project's root folder in VS Code.

  2. Save .vscode/settings.json with the matching feature and step paths.

  3. Press Ctrl+Shift+P and run Developer: Reload Window.

  4. Open a .feature file and try F12 or Ctrl+Click on a step.

If navigation still fails, check the installed extension's name and confirm that the configured folder paths point to your actual feature and step-definition files. This editor configuration is separate from the step paths in defineBddConfig().

10. Understand the generated Playwright tests

After running bddgen, the generated directory contains Playwright test files corresponding to your Gherkin scenarios.

Conceptually, this is what happens:

navigation.feature

Contains the business-readable scenario

navigation.steps.ts

Defines matching TypeScript actions

bddgen

Converts Gherkin scenarios into Playwright test code

playwright test

Runs the generated tests

Remember: We maintain the .feature files and .steps.ts files. We do not edit generated test files.

12. Practice exercise — Login automation

Now apply what you learned to the login feature from Session 1.

The following is a template for an application you choose to test. Replace the sample URL, selectors, and credentials with valid test-environment values.

Feature file

features/login.feature

gherkin

Feature: Login functionality

  Scenario: Login with valid credentials
    Given User is on the login page
    When User enters "testuser" and "testpass"
    And User clicks the login button
    Then User should see the dashboard

Step definitions

steps/login.steps.ts

typescript

import { createBdd } from 'playwright-bdd';
import { expect } from '@playwright/test';

const { Given, When, Then } = createBdd();

Given(
  'User is on the login page',
  async ({ page }) => {
    await page.goto('https://your-test-app.example/login');
  }
);

When(
  'User enters {string} and {string}',
  async ({ page }, username: string, password: string) => {
    await page.getByLabel('Username').fill(username);
    await page.getByLabel('Password').fill(password);
  }
);

When(
  'User clicks the login button',
  async ({ page }) => {
    await page.getByRole('button', { name: 'Login' }).click();
  }
);

Then(
  'User should see the dashboard',
  async ({ page }) => {
    await expect(
      page.getByRole('heading', { name: 'Dashboard' })
    ).toBeVisible();
  }
);

Notice that the And step in the feature file is matched by a When step definition. And inherits the preceding step's context in Gherkin.

This template will not run successfully until you connect it to a real application. For the first verified learning exercise, use the Playwright documentation navigation scenario from Section 6.
